# CitadelIQ --- Claude Code Implementation Plan

## Day 5: PostgreSQL + pgvector Persistence

> **Purpose:** Give Claude Code a clear, incremental implementation
> plan for moving CitadelIQ from Day 4 in-memory semantic search to
> persistent PostgreSQL + pgvector storage.
>
> **Current stage:** Day 5 --- Vector Databases & pgvector\
> **Next stage:** Day 6 --- RAG Fundamentals

------------------------------------------------------------------------

## 1. Project Context

CitadelIQ is an **AI-powered document management and semantic search portal** — a professional,
enterprise-style application, not a chatbot (see `CLAUDE.md` / `.claude/technical-designs/design.md`
for the settled project description; this doc originally called it an "Enterprise AI Knowledge &
Research Platform," which doesn't match the actual product framing).

The current application already supports the Day 4 semantic-search
workflow:

1.  User uploads a document.
2.  Text is extracted.
3.  The document is split into chunks.
4.  Each chunk receives an OpenAI embedding.
5.  Embeddings are currently held in memory.
6.  User searches using a natural-language query.
7.  The query is converted into an embedding.
8.  CitadelIQ calculates semantic similarity and returns the most
    relevant chunks.

### Day 5 objective

Replace the temporary in-memory persistence layer with:

-   PostgreSQL for durable metadata and document/chunk storage.
-   `pgvector` for vector storage and similarity search.
-   EF Core for querying and writing (the ORM), and **FluentMigrator, in a separate
    `CitadelIQ.FluentMigrations` project, for owning and versioning the schema** (EF Core migrations
    are deliberately *not* used).
-   A clean abstraction so the application is not tightly coupled to
    PostgreSQL.

The Day 5 learning goal is to understand the application flow:

**Generate embedding → store embedding → generate query embedding →
vector similarity search → return top-K results.**

This follows the roadmap's Day 5 focus on vector databases, vector
columns/indexes, similarity search, ANN, similarity metrics, metadata
filtering, PostgreSQL, and pgvector.

# 6. Folder Table

Create a `Folders` table.

Suggested fields:

``` text
Id
Name
ParentFolderId
CreatedAtUtc
```

### Requirements

-   `Id` should be a GUID.
-   `Name` is required.
-   `ParentFolderId` is nullable — **but there is exactly one root folder, not an arbitrary set of
    root-level folders.** `Folder.RootId` is the well-known id `Guid.Empty`, always named "Home",
    with a `null` `ParentFolderId`; every other folder has a non-null `ParentFolderId` that
    eventually chains up to that single root. The frontend relies on this well-known id to
    bootstrap without a lookup (`GET /api/folders/root` just echoes `Guid.Empty` back). The
    migration/seed step must insert this one root row (e.g. an idempotent
    `INSERT ... ON CONFLICT (Id) DO NOTHING`, or an application-startup "ensure root exists"
    check) — the current in-memory repository seeds it in its constructor, which has no Postgres
    equivalent.
-   Support nested folders.
-   Configure the self-referencing relationship correctly in EF Core, **with `ON DELETE CASCADE`**
    on the `ParentFolderId` FK — see the cascade-delete addendum near the end of this document for
    why this matters now that folder delete/rename are implemented features, not just future scope.
-   Add a **unique index on `(ParentFolderId, lower(Name))`** to enforce sibling-name uniqueness at
    the database level. Today, `FolderService.CreateFolderAsync`/`RenameFolderAsync` check-then-act
    (`ExistsWithNameAsync` followed by `Create`/`Rename`) with no atomicity — a real race condition
    under concurrent requests, just not one that's ever surfaced against the single-process
    in-memory store. Catch the resulting Postgres unique-violation in the repository/service layer
    and translate it to the same `ValidationException` message
    (`A folder named "X" already exists here.`) the application already returns today, so the API
    contract and frontend error handling don't change.

Do not implement complex folder permissions yet.

# 7. Document Table

Create a `Documents` table.

Suggested fields — **this must match the existing `Document` domain entity's fields, not just a
generic file-metadata table**:

``` text
Id
FolderId
FileName
ContentType
SizeBytes
UploadedAtUtc
ProcessingStatus
FailureReason
```

`ProcessingStatus` and `FailureReason` are not optional additions — they are required. The
existing two-phase upload pipeline (`Uploaded → ExtractingText → Chunking → GeneratingEmbeddings →
Ready/Failed`) persists status transitions on every step, and the frontend polls
`GET /api/documents/{id}/status` against exactly these two fields. A schema without them would
silently break status polling and the "document failed to process: <reason>" toast.

### Requirements

-   Every document belongs to a folder.
-   `FileName` is required.
-   `ContentType` is required.
-   `SizeBytes` should be numeric.
-   `ProcessingStatus` should be a string-backed enum column (mirrors the existing
    `ProcessingStatus` enum: `Uploaded, ExtractingText, Chunking, GeneratingEmbeddings, Ready,
    Failed`) so the value is human-readable directly in the database.
-   `FailureReason` is nullable — only set when `ProcessingStatus` is `Failed`.
-   There is **no `StorageLocation` column** — the existing `LocalDiskDocumentStorage`
    infrastructure derives the file path deterministically from `{documentId}{fileExtension}`
    under the configured `Storage:DocumentsPath` root, so nothing needs to be stored to locate a
    file. Only add a location/key column later if the storage implementation moves to something
    that generates non-deterministic keys (e.g. S3/Blob).
-   Do not store the binary file in this table.
-   Add a foreign key to `Folders`.

Example:

``` text
Documents
------------------------------------------------
Id
FolderId
FileName
ContentType
SizeBytes
UploadedAtUtc
ProcessingStatus
FailureReason
```

# 8. DocumentChunk Table

Create a `DocumentChunks` table. Field names below use the existing domain entity's naming
(`ChunkIndex`/`Text`, not `ChunkNumber`/`Content`) — keep them, since the Application layer's DTOs
and `TextChunker` already use these names.

Suggested fields:

``` text
Id
DocumentId
ChunkIndex
Text
PageNumber
Embedding
ModelName
CreatedAt
```

`PageNumber` and `ModelName` are both real fields on the existing `DocumentChunk`/
`DocumentEmbedding` domain entities and must not be dropped:

-   `PageNumber` (nullable) is already surfaced in `SearchResultDto` and displayed in search
    results per the requirements' "optional page number when available."
-   `ModelName` records which embedding model produced the vector. Without it, a future embedding
    model change (e.g. swapping `text-embedding-3-small` for a different model/dimension) has no
    way to distinguish old vectors from new ones, and mixed-dimension rows would break pgvector
    queries outright.

### Requirements

-   Every chunk belongs to exactly one document.
-   `ChunkIndex` identifies the chunk's position within the document.
-   `Text` contains the extracted text for that chunk.
-   `PageNumber` is nullable — not every source format has page boundaries (e.g. `.txt`/`.csv`).
-   `Embedding` stores the vector generated for that chunk, and `ModelName` records which model
    generated it.
-   Do not create one embedding for the entire document.
-   Each semantic-search unit should be a chunk.
-   **Performance note:** keep `Embedding` and `ModelName` as columns directly on
    `DocumentChunks` rather than a separate `Embeddings` table, even though the existing Domain
    layer models them as two separate entities (`DocumentChunk` / `DocumentEmbedding`) behind two
    separate repository interfaces (`IDocumentChunkRepository` / `IEmbeddingRepository`). Every
    vector search query needs the embedding on the exact row being ranked — a join per query row
    adds cost for no benefit. The two repository interfaces can both be implemented against the
    same physical `DocumentChunks` table; that split is an Infrastructure detail the Application
    layer never needs to know about. **As implemented:** the vector and model name are EF *shadow
    properties* (`Embedding`, `ModelName`) on `DocumentChunk`, not fields on the domain entity, and
    `EmbeddingRepository` attaches them to already-inserted chunks in a single `SaveChanges`. The
    column is nullable because chunks are inserted first; a document only becomes `Ready` (and
    searchable) after embeddings are stored, and a failed document's chunks are deleted.

Example:

``` text
Document
    report.pdf

DocumentChunks

Chunk 1 → "Revenue increased..."
Chunk 2 → "Operating expenses..."
Chunk 3 → "The company expects..."
```

Each chunk has its own embedding.

# 13. Repository Abstractions

The Application layer should depend on interfaces.

Suggested interfaces:

``` csharp
public interface IDocumentRepository
{
    Task<Document?> GetByIdAsync(Guid id, CancellationToken cancellationToken);
    Task AddAsync(Document document, CancellationToken cancellationToken);
    Task DeleteAsync(Guid id, CancellationToken cancellationToken);
}
```

For chunks:

``` csharp
public interface IDocumentChunkRepository
{
    Task AddRangeAsync(
        IEnumerable<DocumentChunk> chunks,
        CancellationToken cancellationToken);
}
```

For vector search — **do not pass `SearchScope`/`currentFolderId` into Infrastructure.** §15 below
(Search Scopes) says folder-scope resolution, including walking descendant folders for "Current
Folder + Subfolders," should happen in application code. Pushing the raw scope/folder-id into the
repository contradicts that and moves a business rule into Infrastructure. Keep
`SearchService` owning scope resolution exactly as it does today (`CLAUDE.md`'s stated design:
"scope resolution and folder-tree walking happen server-side," as an Application-layer
responsibility) and have it pass down an already-resolved id set:

``` csharp
public interface IVectorSearchRepository
{
    Task<IReadOnlyList<DocumentSearchResult>> SearchAsync(
        float[] queryEmbedding,
        IReadOnlyCollection<Guid> eligibleFolderIds,
        int topK,
        CancellationToken cancellationToken);
}
```

This also means the `Ready`-only filter (`ProcessingStatus.Ready`, already applied today before
computing similarity) and the `MaxTopK` clamp both belong in the SQL query this interface executes
— not applied to results afterward in C# — otherwise the DB does the expensive ranking work over
rows that get thrown away anyway.

**As implemented:** `eligibleFolderIds` is nullable (`IReadOnlyCollection<Guid>?`) — `null` means no
folder filter (Entire Portal), which avoids materialising every folder id. `DocumentSearchResult`
carries the chunk and document fields the search DTO needs (chunk/document/folder ids, file name,
content type, chunk text/index, page number, `SimilarityScore` = 1 − cosine distance); `SearchService`
adds the folder-path display. Repository interfaces that became unused were removed
(`IDocumentRepository.GetAllAsync`, `IDocumentChunkRepository.GetByDocumentIdsAsync`,
`IEmbeddingRepository.GetByChunkIdsAsync`/`DeleteByChunkIdsAsync`); embeddings are deleted with their
chunks.

The exact signatures may be adapted to the existing CitadelIQ code.

Do not create unnecessary abstractions merely for abstraction's sake.

# 20. Migration (FluentMigrator)

Schema is owned by the separate **`CitadelIQ.FluentMigrations`** project — not by EF Core
migrations, and not by `Database.EnsureCreated()`. It has no dependency on Domain/Application/
Infrastructure; `CitadelIQ.Api` (the composition root) references it, calls
`AddFluentMigrations(connectionString)` and, in Development, `ApplyDatabaseMigrations()` at startup.
Deployed environments should run migrations explicitly.

Migrations are numbered classes with `[Migration(<yyyyMMddNNNN>)]`, e.g.:

``` text
Migrations/M202609300001_InitialDocumentVectorSchema.cs
```

The initial migration creates:

``` text
vector extension
Folders           (self-referencing FK, ON DELETE CASCADE)
Documents         (FK -> Folders, ON DELETE CASCADE)
DocumentChunks    (FK -> Documents, ON DELETE CASCADE)
```

plus:

-   the unique index on `(ParentFolderId, lower(Name))`,
-   the `Embedding vector(1536)` column on `DocumentChunks` and an HNSW cosine index
    (`USING hnsw ("Embedding" vector_cosine_ops)`),
-   the seeded root "Home" folder (`Id = Guid.Empty`).

FluentMigrator has no pgvector type or expression-index support, so those pieces use
`Execute.Sql(...)`. The vector dimension is therefore fixed *in the migration* (1536 for
`text-embedding-3-small`); changing the embedding model/dimension requires a new migration (and
re-embedding), not just a config change. pgvector caps HNSW/IVFFlat at 2000 dimensions.

Applied migrations are tracked by FluentMigrator in its `VersionInfo` table.

# 25. Error Handling

Handle at least these cases:

### Database unavailable

Return a controlled application error.

### Embedding generation fails

Do not silently save a document as if it were fully indexed.

### File save succeeds but database save fails

Clean up the orphaned file where practical.

### Database save succeeds but embedding processing fails

Avoid leaving an apparently searchable document without embeddings.

### Invalid upload

Reject before processing.

### Empty extracted text

Reject or mark processing failure.

### Search with no indexed documents

Return an empty result set rather than an exception.

Because semantic similarity alone cannot enforce application-level

Separately from the vector data. The database stores metadata and

# 36. Addendum — Delete/Rename and Background-Processing Concerns Not Covered Above

This document predates two features that now exist in CitadelIQ (folder/document delete, folder
rename) and doesn't account for the existing fire-and-forget background processing dispatcher.
Both matter for the Postgres migration and aren't addressed by the sections above.

## 36.1 Cascade delete

Today, `FolderService.DeleteFolderAsync` orchestrates deletion entirely in application code: it
walks the full descendant folder tree (`IFolderRepository.GetDescendantIdsAsync`, already
recursive), loads every document anywhere in that subtree, deletes each document's chunks,
embeddings, and stored file via `IDocumentService.DeleteDocumentsAsync`, and only then removes the
folder records. `DocumentService.DeleteDocumentAsync` does the equivalent single-document version:
delete embeddings → delete chunks → delete the on-disk file → delete the document record, in that
order, so a crash mid-delete never leaves orphaned chunks/embeddings pointing at a missing document.

With the FK relationships and cascade rules proposed in §6/§7/§8 above (`ON DELETE CASCADE` on
`Folders.ParentFolderId`, `Documents.FolderId`, and `DocumentChunks.DocumentId`), the *database
records* for an entire folder subtree can collapse to a single `Remove(folder)` +
`SaveChangesAsync()` — Postgres cascades the rest via the FK chain, and the manual multi-step
orchestration in `FolderService`/`DocumentService` can be simplified accordingly.

**What cascade delete cannot do**: clean up files on disk. `IDocumentStorage.DeleteAsync` calls are
outside the database's knowledge entirely. The correct order is still: **query the affected
document ids and file extensions first** (before deleting anything), delete the DB rows (letting
cascade handle folders/documents/chunks in one `SaveChangesAsync`), and only then delete each
file from disk. If file deletion fails partway through, the DB is already consistent — an orphaned
file on disk is a much smaller problem than an orphaned DB row pointing at a missing file, and
matches the existing philosophy noted in `CLAUDE.md` (orphaned files after a restart are an
accepted, documented tradeoff; orphaned DB rows are not).

## 36.2 Rename

`Folder.Rename` reuses the same name validation as `Folder.Create`; `FolderService.RenameFolderAsync`
already rejects renaming the root/Home folder and rejects a sibling name collision (except when the
new name differs from the current one only by case) via the same `ExistsWithNameAsync` check folder
creation uses. Once the `(ParentFolderId, lower(Name))` unique index from §6 exists, the
collision check becomes redundant with the DB constraint — keep the application-level check for a
fast, friendly error message on the common case, but still catch the DB unique-violation as a
fallback for the race-condition window between the check and the write (see §6).

## 36.3 DbContext lifetime vs. the existing background dispatcher

`BackgroundDocumentProcessingDispatcher` schedules `Task.Run` on a **new DI scope** specifically
because the HTTP request's own scope is disposed once the response is sent (documented in
`CLAUDE.md`'s "Upload & processing pipeline" section). This is already correct practice today with
an in-memory store, where it doesn't matter much. It becomes load-bearing the moment a `DbContext`
exists: `DbContext` instances are not thread-safe and are not meant to be shared across concurrent
operations. If the background task's new scope doesn't resolve its own fresh `DbContext` (separate
from whatever the original HTTP request's scope used), the two will race and throw
`InvalidOperationException: A second operation was started on this context before a previous
operation completed`. Phase 6/7 in §28 should explicitly verify the dispatcher resolves a new
scoped `DbContext` per background task, not just a new scope in the abstract.
